# AGENTS.md

This file provides guidance to AI tools like Claude Code or Codex when working with code in this repository.

## Project

Vite + React + TypeScript frontend for Soldank++ (soldank-plus-plus), a Soldat-inspired game: player/map/clan/country rankings, capture/medal events and time-attack records. Consumes a separate NestJS backend (spp-webstats) over REST at `VITE_API_BASE_URL`, with no mock fallback. Today the real backend only implements `GET /maps`, `GET /maps/:id` and `GET /events`; the `users`/`clans`/`countries`/`stats` API modules and their pages still talk to endpoints that don't exist on the backend yet, so they'll error until the backend catches up.

## Build

Requires Node.js v16+.

```
npm install
npm run dev
```

`npm run build` builds against the real backend (`VITE_API_BASE_URL`, see `.env` / `.env.development`). Path alias `@/*` resolves to `src/*`.

`npm run generate:api-types` regenerates `src/api/generated/` from the backend's live OpenAPI schema (`http://localhost:3000/api-json`, requires the backend running locally) via `openapi-codegen`, then reformats it (the tool doesn't pick up this repo's `.prettierrc`). Never hand-write request/response types or React Query hooks for endpoints the backend documents; use the generated ones instead (see Architecture).

## Architecture

Feature-oriented split under `src/`:

- `src/api/generated/`: generated by `openapi-codegen` (config in `openapi-codegen.config.ts`) from the backend's OpenAPI schema, currently covering `maps`/`events`. `sppComponents.ts` and `sppSchemas.ts` are overwritten on every regeneration (per-endpoint React Query hooks like `useMapsControllerFindAll`, and DTO types like `FindAllMapsDto`); `sppFetcher.ts`/`sppContext.ts`/`sppUtils.ts` are generated once and safe to hand-edit (`sppFetcher.ts` has the real `baseUrl`); `sppErrors.ts` is entirely hand-written (never touched by the generator) for pulling a message out of the untyped `error` these hooks return, since the backend doesn't document error responses.
- `src/api/`: one file per resource (`maps.ts`, `events.ts`, `users.ts`, `clans.ts`, `countries.ts`, `stats.ts`). For endpoints the backend documents, use the generated hooks in `src/api/generated/` directly from your own hook in `src/hooks/`, not these files. `src/api/client.ts` exports `legacyApiClient`, a loosely-typed fallback for endpoints the backend doesn't implement/document yet (`users`, `clans`, `countries`, `stats`, and a few `events` sub-resources) — migrate a resource's callers to the generated hooks and delete its `legacyApiClient` usage once the backend adds it to the OpenAPI schema.
- `src/hooks/`: one folder per resource (`maps/`, `events/`, `users/`, ...); each hook exposes `{ data, loading, error, totalPages }`-style state. For endpoints the backend documents, this is a thin wrapper around a generated hook from `src/api/generated/sppComponents.ts` (see `useMaps.ts`/`useMap.ts`/`useEvents.ts`); for the rest, hand-rolled `useState`/`useEffect` calling `legacyApiClient`. `src/hooks/core/` holds cross-cutting hooks (`useDebounce`, `UseMobile`, `ScrollToTop`).
- `src/types/`: one file per data shape returned by the backend (`map.ts`, `event.ts`, `user.ts`, ...). For endpoints the backend already exposes (`maps`, `events`), these re-export/derive from `src/api/generated/sppSchemas.ts` rather than redeclaring fields by hand.
- `src/pages/`: one folder per route (`Maps/`, `Map/`, `Account/`, `Ranking/`, `Servers/`, ...), composed from the matching `src/components/layouts/<Area>/` components. `src/config/Routes.tsx` is the route table consumed by `src/main.tsx`.
- `src/components/layouts/`: page-specific layout components, grouped by area (Ranking, Account, Maps, Servers, Landing, ...).
- `src/components/ui/shadcn/`: shadcn/ui primitives. `src/components/ui/custom/`: shared custom components (core layout pieces like Header/Footer, and reusable feature components like tables, pagination, search).

Global tag styles (`h1`-`h4`, `p`, `a`) are set once in `index.css`; don't re-add Tailwind classes for them in components. Loading states use the shared `Skeleton` component, never a literal "Loading..." string.

## Code style

Comments should be short and only where they add real value:

- Delete comments that just restate what the code obviously does.
- No section-divider comments (e.g. `// --- section ---`).
- No meta-commentary about the coding process ("Note: I decided to...").
- Don't reference other files, languages, or implementations that might not exist in this repo. Keep comments self-contained.
- A single-sentence comment should not end with a trailing period. Only use periods when a comment has multiple distinct sentences.
- Do keep short explanations of genuinely non-obvious behavior or the root cause of a workaround.

Never use em-dashes (—) or a hyphen as sentence punctuation (word - word), anywhere: code, comments, docs, commit messages. Use a comma, period, colon, or parentheses instead. Hyphens inside compound words and identifiers (`well-known`, `single-sentence`, `spp-webstats`) are fine.

Git commit messages are short and in imperative mood, no type prefix (no Conventional Commits `feat:`/`fix:`/etc.). No `Co-Authored-By` trailer.
