# AGENTS.md

This file provides guidance to AI tools like Claude Code or Codex when working with code in this repository.

## Project

Vite + React + TypeScript frontend for Soldank++ (soldank-plus-plus), a Soldat-inspired game: player/map/clan/country rankings, medal positions and time-attack records. Consumes a separate NestJS backend (spp-webstats) over REST at `VITE_API_BASE_URL`, with no mock fallback.

Every gamemode gets its own Postgres database with its own schema, so the backend namespaces its data routes by gamemode: `maps`, `stats`, `positions`, `users`, `clans` and `countries` all live under `/climb/...` (including nested sub-resources like `/climb/maps/:id/positions` and `/climb/users/:id/stats`), and the backend modules mirror that under `src/features/climb/`. `GET /gamemodes` is the only mode-agnostic route: it lists every gamemode with an `available` flag saying whether a database is wired up for it, and Climb is the only available one so far. The frontend keeps the choice in a `?gamemode=` query param (`useGamemode`), and a mode that is not available renders a coming soon state instead of firing requests. `PUT`/`DELETE /climb/users/:id` are deliberately not implemented (no auth on the backend yet), so don't add frontend calls to them.

## Build

Requires Node.js v16+.

```
npm install
npm run dev
```

`npm run build` builds against the real backend (`VITE_API_BASE_URL`, see `.env` / `.env.development`). Path alias `@/*` resolves to `src/*`.

`npm run generate:api-types` regenerates `src/api/generated/` from the backend's live OpenAPI schema (`http://localhost:3000/api-json`, requires the backend running locally) via `openapi-codegen`, then reformats it (the tool doesn't pick up this repo's `.prettierrc`). Never hand-write request/response types or React Query hooks for endpoints the backend documents; use the generated ones instead (see Architecture).

## Tests

No test runner is configured; there are no test files. `npm run pre-push` (husky) runs `npm run lint` and `npm run type-check`, and both have to stay clean.

## Architecture

Feature-oriented split under `src/`:

- `src/api/generated/`: generated by `openapi-codegen` (config in `openapi-codegen.config.ts`) from the backend's OpenAPI schema, covering `maps`/`events`/`stats`/`users`. `sppComponents.ts` and `sppSchemas.ts` are overwritten on every regeneration (per-endpoint React Query hooks like `useMapsControllerFindAll`, and DTO types like `FindAllMapsDto`); `sppFetcher.ts`/`sppContext.ts`/`sppUtils.ts` are generated once and safe to hand-edit (`sppFetcher.ts` has the real `baseUrl`); `sppErrors.ts` is entirely hand-written (never touched by the generator) for pulling a message out of the untyped `error` these hooks return, since the backend doesn't document error responses. The backend's `@Serialize()` decorator wraps every non-paginated response in `{ data: ... }` at runtime and declares that envelope in its Swagger annotation (pass `{ isArray: true }` for handlers returning an array), so the generated response types for those endpoints (e.g. `MapsControllerFindOneResponse`, `UsersControllerFindActivityResponse`) already have a `data` property with the right shape — no manual casting needed.
- `src/hooks/`: one folder per resource (`maps/`, `positions/`, `users/`, `clans/`, `gamemodes/`, ...); each hook exposes `{ data, loading, error, totalPages }`-style state and is a thin wrapper around a generated hook from `src/api/generated/sppComponents.ts` (see `useMaps.ts`/`useMap.ts`/`useClan.ts`). Filtering, sorting and ranking belong in the request the hook sends, not in the component that renders the rows. `src/hooks/core/` holds cross-cutting hooks (`useDebounce`, `UseMobile`, `ScrollToTop`).
- `src/types/`: one file per data shape returned by the backend (`map.ts`, `position.ts`, `user.ts`, `stat.ts`, `gamemode.ts`, ...), re-exporting or deriving from `src/api/generated/sppSchemas.ts` rather than redeclaring fields by hand.
- `src/pages/`: one folder per route (`Maps/`, `Map/`, `User/`, `Ranking/`, `Servers/`, ...), composed from the matching `src/components/layouts/<Area>/` components. `src/config/Routes.tsx` is the route table consumed by `src/main.tsx`. A `Children/` folder holds pages you navigate to from the page above it (the profile tabs, the ranking tabs, the map opened from the map list), so every file in one has its own route. A section that only renders inside its parent page belongs in `src/components/layouts/<Area>/` and is imported by the page directly, without a wrapper in `Children/`.
- `src/components/layouts/`: page-specific layout components, grouped by area (Ranking, User, Maps, Servers, Landing, ...).
- `src/components/ui/shadcn/`: shadcn/ui primitives, kept where the shadcn CLI expects them (`src/lib/utils.ts` holds its `cn()` helper). `src/components/ui/custom/`: shared custom components (core layout pieces like Header/Footer, and reusable feature components like tables, pagination, search, the gamemode picker).
- `src/utils/`: framework-free helpers shared across features (`format.ts` for record times and dates, `countryFlags.ts`). Timestamps arrive from the API as unix milliseconds and are formatted here, never on the backend, so they render in the viewer's timezone.

Global tag styles (`h1`-`h4`, `p`, `a`) are set once in `index.css`; don't re-add Tailwind classes for them in components. Loading states use the shared `Skeleton` component, never a literal "Loading..." string.

## Code style

Comments should be short and only where they add real value:

- Delete comments that just restate what the code obviously does.
- No section-divider comments (e.g. `// --- section ---`).
- No meta-commentary about the coding process ("Note: I decided to...").
- Don't reference other files, languages, or implementations that might not exist in this repo. Keep comments self-contained.
- A single-sentence comment should not end with a trailing period. Only use periods when a comment has multiple distinct sentences.
- Do keep short explanations of genuinely non-obvious behavior or the root cause of a workaround.

Never use em-dashes (—) or a hyphen as sentence punctuation (word - word), anywhere: code, comments, docs, commit messages. Use a comma, period, colon, or parentheses instead. Hyphens inside compound words and identifiers (`well-known`, `single-sentence`, `spp-webstats`) are fine.

Git commit messages are short and in imperative mood, no type prefix (no Conventional Commits `feat:`/`fix:`/etc.). No `Co-Authored-By` trailer.
